# Codex 执行任务：为 StarLedger 建立低 Token 成本的自动回归测试

> 仓库：`No3456bite/starledger-web`  
> 目标：减少历史 Bug 反复出现，以及用户手工复测和 AI 使用虚拟浏览器的次数。  
> 本任务是**测试基础设施建设**，不是功能重构。请直接执行，并以 PR 交付；不要直接合并或部署。

## 一、先理解现有项目（必须）

1. 从最新 `main` 创建独立分支，例如 `test/playwright-regression`。
2. 阅读 `AGENTS.md`、`docs/ARCHITECTURE.md`、`README.md`，检查当前仓库结构和 `.github/workflows/pages.yml`。
3. 阅读 `scripts/validate-build.mjs` 与 `scripts/test-*.cjs`，确认现有 Node 测试覆盖内容。**复用现有检查，不要复制一套相同测试。**
4. 检查页面真实 DOM、现有交互函数、数据初始化方式；以下测试用例是行为目标，**不要想当然假定选择器、按钮文案或内部实现存在**。
5. 先提交简短执行计划，说明将改动哪些文件、哪些行为能可靠自动测试、哪些只能真机验收；然后实施，不需要用户逐项确认。

## 二、核心原则

- **自动化优先于 AI 操作浏览器**：使用 Playwright 的普通脚本测试在本地/GitHub Actions 中运行。每次 CI 执行不调用 GPT、Codex 或其他模型，也不调用 AI 浏览器代理。
- **测试历史 Bug，不求一次测完所有功能**：先建立最小、稳定、可扩展的冒烟测试集，预计 4–8 个独立用例，后续遇到复发性 Bug 再增补。
- **一次测试只验证明确行为**：使用可观察的状态断言，不要用“点击不报错”替代正确性验证；失败时要能明确定位是哪个场景。
- **隔离真实数据**：仅在本地静态服务、独立浏览器上下文和测试样本中运行；禁止连接生产数据、真实云同步/WebDAV、用户 iCloud 文件、个人账本或真实凭据。不得执行会影响线上数据的写入、清空、迁移或删除操作。
- **最小改动**：不要趁机重写 `app.js`、`ui-runtime.js`、`recognizer.js` 或 CSS。必要时允许少量稳定的 `data-testid` / 无业务影响的测试入口，并说明理由。
- **不掩盖失败**：禁止通过删除断言、无限重试、任意增加 `waitForTimeout`、伪造测试数据或忽略异常来让 CI 变绿。确实无法自动验证的项目要明确列为“待人工测试”。
- **遵守现有仓库规则**：本任务自己的“必须 PR、不得直接合并”优先适用于本次交付；不要借此任务变更整个项目的发布政策。

## 三、实施内容

### A. 建立 Playwright 测试基础

- 选择适合当前纯前端静态 Web 项目的最小方案：`@playwright/test` + 本地静态 HTTP 服务，尽量不新增运行时框架。
- 如仓库缺少 `package.json`，只增加测试所需的最小 `package.json`、锁文件及 npm 命令，如 `npm run test:e2e`、`npm run test:e2e:webkit`（按实际配置调整）。
- 新增 `playwright.config.*` 和 `tests/e2e/`。用 Playwright `webServer` 管理本地 HTTP 服务，基准地址为 `127.0.0.1`，测试不依赖 GitHub Pages 在线站点。
- 优先使用稳定的语义定位（role / label / text）或必要的 `data-testid`；避免依赖页面元素顺序、随机 ID、脆弱的 CSS 层级。
- 每个测试独立创建/清理上下文和存储状态；不要让上一个测试的账单/缓存影响下一个测试。注意 Service Worker、IndexedDB、localStorage 对隔离性的影响。
- 默认无头模式，有限超时，CI 失败最多重试 1 次；不要在 PR 上做高并发、长时间巡游。

### B. 第一批浏览器回归测试

按**现有项目真实交互**实现。优先级从高到低：

1. **首页冷启动**：能正常加载首页和关键容器，捕获未处理的 JavaScript `pageerror`；不允许仅以 HTTP 200 作为通过标准。
2. **导航与状态恢复**：首页 → 月/年统计 → 账本 → 返回；确认目标页面显示正确、导航未失效、页面没有被意外遮罩拦截。
3. **页面滚动回归**：在足够长的隔离测试数据条件下滚动、切页、返回，检查滚动容器仍能响应；如果无法安全构造足够长的样本，先把该测试列为待实现，不得写一个无有效滚动的“假通过”。
4. **筛选器生命周期**：打开筛选面板 → 操作或滚动 → 关闭 → 再次打开；验证面板可关闭、遮罩清除，关闭后页面交互恢复。
5. **记一笔弹窗生命周期**：打开 → 进入可测试的输入/子面板（若可靠）→ 关闭；确认焦点/遮罩正确恢复，**不向真实账本保存**。
6. **视图切换稳定性**：明暗模式或移动端窄视口下的核心导航（选择其中能稳定断言的一项），确保没有页面不可操作的问题。

上述 6 项不是要求强行写满。如果发现功能依赖特定数据、真实移动 Safari 或无法稳定复现：
- 先实现可真实断言的 4 项左右，并列出其他项目的阻碍与补测条件；
- **禁止**为了达到数量而写无意义断言；
- 已有 Node 单元测试覆盖的数据、备份、OCR 逻辑，本轮不重复造一套 UI 测试。

### C. Safari / WebKit 的处理

- 优先确保 Chromium 冒烟测试在每个 PR 上稳定运行。
- 可增加少量 **桌面 WebKit** 回归测试，至少覆盖导航、筛选器等历史高风险路径；通过独立命令或 `workflow_dispatch` 手动触发即可，避免第一阶段过度增加 CI 复杂度。
- 明确标注：桌面 WebKit **不能替代 iPhone 真机 Safari** 的地址栏展开/收起、软键盘、visualViewport、PWA 等验收。
- 在 `tests/REGRESSION_CHECKLIST.md` 写下真机检查清单，不要声称 CI 已验证这些行为。

### D. 接入 GitHub Actions

- 在现有 `.github/workflows/pages.yml` 基础上增加独立浏览器冒烟测试 Job，或在不重复安装/执行的前提下合理整合；保留原有所有 Node 检查。
- PR 与 `main` 的提交触发快速 Chromium 测试。若现有生产部署在 `main` push 后进行，应确保部署依赖原有验证**及新增冒烟测试成功**，不要绕过任何现有检查。
- 仅安装本轮实际运行的浏览器及依赖。失败时上传 Playwright trace、必要截图和简洁日志；成功时不上传大量视频、截图及 trace。
- `video` 默认关闭；`screenshot` 仅失败时保存；`trace` 仅失败时保留（如 `retain-on-failure`）；禁止在测试日志和附件中输出密钥、个人账单及真实财务信息。
- 限制单个用例的执行时间，测试超过预期耗时应定位原因，而非无上限延长等待。

### E. 建立“Bug 留痕”制度

新增 `tests/REGRESSION_CHECKLIST.md`，至少包含：

- 自动化测试覆盖表：`用例 ID | 历史风险 | 测试文件 | 自动/手动 | 适用浏览器 | 状态`。
- Safari 真机手测清单：地址栏伸缩、键盘弹出与关闭、弹窗/子浮层、滚动容器、PWA/浏览器标签页差异。
- 新 Bug 的处理模板：**复现步骤 → 根因与归属模块 → 最小修复 → 新增或更新回归断言 → 本地及 CI 结果 → 真机剩余风险**。
- 若某类 Bug 当前无法自动化，写清受限原因和人工验证步骤，不可默默跳过。

并在 `AGENTS.md` 中**追加简短规则**：
> 以后修复重复发生或高风险的 Bug 时，优先新增能在 CI 里复现失败并确认修复的回归测试；无法自动化须明确说明原因与人工验收路径。

只追加此必要规则，不重写原有项目原则。

## 四、成本和质量约束

这里有两种不同的成本，不能混为一谈：

1. **GitHub Actions + Playwright**：消耗 CI 执行时间、计算资源和附件存储，**不按大模型 Token 计费**（前提是测试脚本没有主动调用模型 API）。
2. **AI 阅读/操作浏览器**：会消耗模型使用量。本任务不得让 Codex 每次自动打开托管浏览器逐页巡检。AI 应以代码审查、失败日志/trace 分析为主，只有自动测试无法解释的失败才进行交互式排查。

避免海量打印 DOM、整页截图、长日志；报告只保留能复现和判断问题的证据。不要为减少成本而牺牲关键断言。

## 五、验收标准（Definition of Done）

- [ ] 建立可在本地一条命令运行的 Playwright 测试集，并提供运行说明。
- [ ] 至少有 4 个**真实可验证、非空断言**的浏览器测试场景；若客观上不足 4 个，必须明确阻碍，不得伪造结果。
- [ ] 新增测试在 GitHub PR 上执行，保留原有 Node/构建验证，且不会因为未合并的 PR 而发布生产页面。
- [ ] 失败可从测试名称、错误输出及按需保存的 trace/截图定位到具体场景。
- [ ] 测试彼此隔离，未读取或更改用户真实账本/云同步数据。
- [ ] `tests/REGRESSION_CHECKLIST.md` 记录自动化覆盖与真机待测项目。
- [ ] 检查本次 `git diff`，没有无关 UI 设计调整、数据结构变化、大范围重构或业务行为改动。
- [ ] 本地测试与已有 Node 校验通过；CI 实际运行结果如实汇报。遇到环境限制不要假称通过。
- [ ] 创建 PR，**不要合并到 `main`**，也不要私自修改当前线上部署设置。

## 六、最终交付报告格式

PR 描述必须包括：

1. 新增文件/修改文件列表、每项的目的。
2. 已覆盖的历史 Bug 场景和对应测试 ID。
3. 本地命令、执行结果、GitHub Actions 状态（区分真实通过 / 未运行 / 失败）。
4. 目前不能自动化的 Safari/iPhone 行为及建议真机测试步骤。
5. CI 大致运行耗时（用实际记录，不要编造），对 GitHub Actions 资源和 AI Token 消耗的影响。
6. 哪些源代码被改动，以及为什么无法只修改测试文件。
7. PR 链接，供 ChatGPT 做第二轮代码审查。

**本任务结束条件：PR 已创建、测试证据齐全、等待用户审核。禁止自行合并。**
