## 1. 核心决策与不变量

**架构决策：继续保留 IndexedDB 作为本地存储，保留现有通用 CSV 作为导入/导出交换格式，保留完整 ZIP 作为真正的完整备份。暂不迁移到 SQLite，也不为了“关系型”而重写整个应用。**

以下业务不变量必须可测试，若现有业务约定与此冲突，先列出冲突供用户确认：

- 每条账单有唯一且稳定的 `id`；同一 ID 更新/合并不应变成两笔，新增记录不应意外覆盖旧记录。
- 支出减少对应账户余额，收入增加余额；同币种普通账户间转账不改变合计资产，且**不计入收入/支出**；借贷、信用卡、余额调整遵守各自既有业务语义。
- 修改或删除一笔旧账后，余额、净资产和分类统计必须重新得到一致结果；未校准账户、未能换算的外币不得静默显示为准确净资产。
- 涉及多份关联数据的业务操作，不能留下无法识别的“半次成功”；单笔 IndexedDB 事务可保证原子性的地方应使用同一个提交边界。外部多个 CSV/JSON 文件无法获得跨文件数据库事务，需要单独的失败恢复与验证策略，不得承诺虚假的全平台原子性。
- 重命名/删除账户不会静默遗失交易，不会让旧账户配置与流水不一致；发生错误时原数据可恢复。
- 导入合并不应静默丢掉既有数据；删除状态与旧设备合并的行为必须明确，不能让用户误以为完整 ZIP 一定能传播删除状态。
- 全量 ZIP 包括主账本流水、设置、关联关系及必要元数据；单个 CSV **不**代表完整恢复。旧 CSV、旧 ZIP 应有向后兼容路径。
- 数据仍属用户：可离线使用，可导出可验证的数据，恢复过程要有明确预览、备份和失败回退。

## 2. 现状与发现（源码静态审查；实施时复核）

### 2.1 已经具备的能力，原则上保留

- `app.js` 的 `COLS` 是 19 列：`id,date,type,category,subcategory,amount,account,account2,reimbursement,note,image,role,tags,currency,merchant,book,extras,created_at,updated_at`。
- `csvParse/csvWrite` 保持统一交易流水和兼容旧版导入模板。
- `db()` 打开 `star-ledger-local-1`，当前版本创建单个 IndexedDB object store `state`；`putBundle` 可以在一次 `readwrite` 事务中写多个 key，且存在 `localStorage` 应急后备路径。
- 账单及各主账本配置/关联存储在不同逻辑 key；并非 SQLite 式的独立实体表。目前应用在内存中使用 `rows` 并通过 JS 筛选、汇总、计算余额。
- `accountData / accountRawNet / accountViewData / financial` 计算账户与净资产；`mergeSourceRows` 按 `id` 与更新时间合并记录。
- 完整 ZIP 包含各账本 CSV、`StarLedgerConfig.json`、`StarLedgerRelations.json`、摘要，并校验 CRC/内容码。导入前存在预览/本机恢复点流程。
- 工作区和云备份属于额外路径，iOS Safari 不具备持久文件夹写入能力。**不要因为本任务破坏现有手机使用路径。**

### 2.2 需要验证和/或加固的具体风险

**A. 账户改名/删除的提交边界。** `renameAccount` 当前先将历史流水的 `account/account2` 替换并调用 `localWrite('replaceLedger', ...)`，再修改 `accountProfiles / accountTypes / accountOrder / accountAliases` 等配置并调用 `savePrefs`。`deleteAccount` 也有流水与配置分步保存。只要两步间出错就可能出现不一致，尤其需分别测试纯浏览器模式和工作区模式。注意复核 `replaceLedger` 是否意外改动 `lastExportAt/lastExportName` 等与导入有关的元数据。

**B. 账户引用以名称而非永久 ID 表示。** `account`、`account2` 保存名称；`accountProfiles` 等以名称为 key。当前重命名通过批量迁移账单来适配。短期可正常运行，但必须保证改名/迁移一致性；长期引入稳定 ID 需要单独设计，不得直接修改 CSV 字段导致旧导入不兼容。

**C. 删除标记与跨设备合并。** `mergeSourceRows` 会按 `id/updated_at` 选择记录，并过滤 `isDeletion`；存在 `deletionRecord`。但完整 ZIP 导出可见账单，README 明示跨端删除后合并可能有风险。必须测试：“A 删除、B 保留、双方离线更新、后来合并”是否导致删除记录复活，明确区分工作区同步、完整 ZIP 合并和覆盖恢复。方案选择前先给出期望语义和兼容影响。

**D. 导入数据有效性及精度。** 当前 `csvParse` 对列读取以字符串为主，表单的 `validate` 检查了一部分必填/正金额条件。需要检查 CSV/ZIP 入口是否执行等价规则，避免空 ID、重复 ID、无效日期/金额、异常币种、孤立账户/关联或格式损坏直接影响统计。不要简单拒绝全部历史合法数据；新增兼容读取+诊断策略。检查金额/汇率浮点运算下的舍入和不平衡边界，优先用测试确认，未必需要立刻重写货币引擎。

**E. 失败时内存状态与磁盘状态。** `savePrefs` 在某些路径先更新内存中的 `prefs` 再尝试持久化；`putBundle` 在 IndexedDB 失败时可能走 `localStorage` 后备。需要验证写入失败、关闭重开、恢复与自动备份内容码之间是否一致。关注“本机回退写成功但下次优先读取旧 IndexedDB 值”的可能性，采用可复现故障注入验证，不做推断式改码。

**F. 同一账本历史余额/账户配置的可追溯性。** 测试 `calibration`、余额调整、外币参考汇率变更、含未换算账单、信用卡借贷、多账本切换。确保账户更名、批量修改和导入后净资产与既有口径一致。

## 3. P0：现在执行——测试与最小安全加固

### P0-A 数据规则与回归样本（先做，不改变生产行为）

建立专门的合成数据 fixture 与自动测试，至少覆盖：

1. 基础四类型：收入、支出、转账、借贷，以及余额调整；账户 A/B、同账户、不同币种、外币缺汇率。
2. 账户创建、改名（含主/对方账户）、迁移、删除（无账单/有账单、迁至其他账户/连账单删除），验证配置、别名、顺序、交易数和余额。
3. 手工修改既有账单金额、账户、类型、日期，批量改动、撤销/恢复，金额/余额/统计不残留旧值。
4. CSV 往返、旧格式兼容、重复 ID、冲突时间戳、损坏输入与异常值的诊断。
5. 多主账本隔离及切换、完整 ZIP 导出/解析/恢复、导入前恢复点、内容码、关联 JSON 完整性。
6. 删除标记：工作区三来源合并、ZIP 合并、两端分别修改/删除、相同时间戳、旧备份恢复；明确“合并”和“覆盖”差异。
7. 故障注入：提交前失败、事务中断、配置写入失败、外部文件写入失败、空间不足、IndexedDB 拒绝、localStorage 回退与随后重启读取。

先记录当前行为作为基线，判定哪项违反了既有契约；每项修复应随对应自动测试一起提交，避免只靠 UI 验收。

### P0-B 最小修复策略

- 优先让账户重命名/删除的**本地 IndexedDB 路径**通过一次 `putBundle` 写入账单、配置和相关状态，并且成功后再更新可见内存状态；验证失败不产生半次成功。
- 工作区外部 CSV 与 JSON 文件因非原子写入，应保留可恢复快照或明确执行顺序、重试/回滚与诊断；不得为了追求形式上原子而采用不可靠的“删旧再写新”。
- 修复经测试证明的导入/合并/删除问题；无证据的猜想只记录，不做大规模重构。
- 对导入引入“校验/预览/明确告警”而不是静默丢弃；保持旧格式正常数据可迁移。
- 补充自动化测试并在 `README.md` 或架构文档中更新用户可见的删除同步限制（若仍存在）。

### P0 完成标准

- 不修改 `COLS` 19 列对外契约；不强制新增数据库、框架、服务端或账号系统。
- 关键资金操作及异常恢复测试可以重复执行，测试失败会阻止发布。
- 本地账户改名/删除的账单与配置要么一致提交，要么旧数据保持可恢复；工作区路径具备明确恢复策略。
- CSV 单文件/ZIP 全量的职责不变，旧备份能读取，并且用合成账本做完 ZIP 实际恢复验证。
- UI、OCR、移动端体验没有无关变化。无法自动验证的 iPhone Safari 路径列出人工检查项。
- 提供简明的“更改前/更改后”说明、测试命令与结果、已知剩余风险、回退点。

## 4. P1：未来候选——内部实体 ID 规范化（本轮不执行）

目标：**内部引用稳定，外部 CSV 仍可读。** 先写设计文档比较选项（不是先改代码）：

- 给账户稳定 `account_id`；以后视需要给主账本、分类、商家等实体 ID，但不必“一切都加表/加 ID”。
- 业务对象使用 ID 引用，界面显示名称；账户改名不应逐条改写历史交易语义。
- **明确“名称重复/旧名别名/删除再新建同名账户/跨主账本同名账户”的规则**。
- 导入旧 CSV 时通过映射表把账户显示名解析成内部 ID，不能自动猜测有歧义的名称；必要时用户选映射。
- 对外导出的传统 19 列 CSV 可继续输出可读名称；完整 ZIP 保存无损的 ID 与映射信息、模式版本和迁移版本，设计往返后的 ID 稳定策略。
- 对未升级的客户端/旧备份制定向后兼容与降级规则；批量数据迁移必须有原始快照、可重复执行、失败回滚、迁移后数量/金额/关系对账。
- 测量复杂度与风险。若现有名称引用配合 P0 的原子操作已满足需求，可暂不实施 P1。

请将 P1 设计、迁移风险、测试样例和建议拆分成独立任务，**先请用户批准**。

## 5. P2：未来候选——IndexedDB 逐笔结构化存储（本轮不执行）

仅当数据量、查账性能、同步复杂度或开发维护成本确实构成问题时评估：

- 当前每个账本保存整份 CSV 字符串；备选为 IndexedDB 中单笔账单对象、索引、配置与关系实体存储。
- 提供实际性能测试与替换收益，区分缓存/排序瓶颈、浏览器限制和数据体积问题。
- 设计从旧 `state` 数据键迁移到新版数据库 object store 的方案；考虑 schema version、断点恢复、兼容导出、回滚及移动端空间限制。
- 不以“SQL 更专业”为理由迁移到 SQLite。IndexedDB 足够时继续使用它。

### 明确的最终目标

StarLedger 的专业化不是把一张 CSV 拆成越多表越好，而是：**流水准确、账户引用一致、导入与备份可恢复、跨设备冲突可解释、用户始终能带走自己的数据。**
