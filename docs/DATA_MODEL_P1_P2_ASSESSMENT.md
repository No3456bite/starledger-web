# P1 / P2 设计评估（未实施）

基于 2026-10-16 的 P0 检查。当前仍使用 19 列 CSV、按账户名称引用、IndexedDB `state` 键值存储；本评估不改变数据结构。

## P1：账户永久 ID

**收益。** 改名不必批量改写历史账单，别名和跨设备合并可以建立明确身份。当前 P0 的原子提交已解决本地改名时的半次写入，故 P1 暂无紧迫性。

**建议设计。** 只给账户先加 UUID；主账本 ID 必须作为作用域。同一主账本内名称可改，旧名保留为别名，但别名不能自动匹配到多个 ID。删除后重建同名账户分配新 ID；跨主账本的同名账户互不关联。旧 CSV 仍按名称导入导出，内部导入时用当前主账本的映射表解析；遇到重名、旧别名冲突时要求用户选择。完整 ZIP 另存带版本的 ID 映射和账单 ID 引用，以保证导出再导入的 ID 稳定；未升级客户端只读取传统 19 列，但会丢失内部身份信息，需在产品上明确提示。

**迁移与风险。** 从旧账户名称建立映射时先导出并校验完整 ZIP，再按主账本逐个生成映射。每次迁移记录版本和来源内容码，使重试幂等；提交后对比账单数、所有 `account/account2` 引用、余额、分类汇总与关系数，失败则恢复旧快照。最大风险是同名复用或旧别名冲突导致误合并，以及老客户端回写覆盖新身份信息。应先设计双写期和降级读取规则，再开发。

**独立任务与测试。** 先确定 ID 作用域及冲突交互；再设计 ZIP 扩展；再做离线迁移和回滚原型；最后测“改名 → 删除 → 同名重建”、同名跨账本、旧 CSV 映射歧义、旧客户端回写、两端离线改名和 ZIP 往返。建议等真实改名/合并痛点明显时再批准实施。

## P2：逐笔结构化 IndexedDB

**收益条件。** 只有当实际账单量导致启动、查账或保存明显变慢，或整份 CSV 写入限制同步和恢复时，才值得改。当前尚无跨设备、移动端的可重复性能数据，不能认定它优于现状。

**建议先测。** 用合成数据在低端手机和桌面浏览器分别测 1 千、1 万、5 万笔的启动解析、单笔编辑、搜索、完整 ZIP 导出、IndexedDB 占用与存储失败率；记录设备、浏览器版本与耗时分位数。还应分离渲染、排序和存储耗时，避免把 UI 瓶颈误归因给 CSV。

**若确有收益的迁移路径。** 提升数据库 schema version，新建逐笔账单 store 和 `id`、日期、账本等必要索引；保留旧 `state` 原始键作为恢复源，按主账本分批迁移并记录进度和校验结果。迁移完成前继续从旧键读取；完成后仍由同一导出层生成传统 CSV 和完整 ZIP。回退版本需要可读的旧数据或明确的降级导出。需验证移动端空间不足、事务中断、断点重试、旧 ZIP 导入和升级后回退。不要为此引入 SQLite 或必须联网的服务。

**建议。** 当前维持 IndexedDB 整份 CSV。先建立性能基线与阈值，再由用户单独决定是否启动 P2。
